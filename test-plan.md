# План разработки: Elytra + Kek Nuker для Meteor Client 1.21.11

Статус: черновой план перед созданием исходного кода

## 1. Цель первой версии

Создать отдельный Fabric/Meteor-addon для Minecraft 1.21.11, который:

1. Работает рядом с Meteor Client 1.21.11-75 и Musheor 1.6.4.
2. Реагирует только когда модуль `KekNuker` активен.
3. Фиксирует подтвержденное разрушение блока непосредственно под игроком.
4. Переводит управление полетом в конечный автомат:
   - ожидание;
   - выбор целевого блока и точки над ним;
   - первый быстрый вектор от текущей позиции к точке над блоком;
   - второй вертикальный вектор вниз под углом 90 градусов;
   - восстановление обычного управления или аварийная остановка.
5. Имеет режим отладки: состояние автомата, координаты, найденная поверхность и причина остановки.

Первая версия должна проверяться на локальном/тестовом сервере или сервере, где такое поведение разрешено. Совместимость с Grim означает отсутствие ложных предположений о клиентской физике, а не обещание обхода античита.

## 2. Что уже найдено в окружении

- Minecraft: `1.21.11`
- Meteor Client: `1.21.11-75`
- Java в системе: `26`; для проекта лучше зафиксировать Java `21`, потому что локальные моды собраны под Java 21 и этот вариант ближе к официальному шаблону.
- Fabric Loader из Musheor: `0.18.2`
- Musheor: `musheor-1.6.4 1.21.11.jar`
- Entrypoint Musheor: `musheor.musheor`
- Musheor содержит классы:
  - `musheor.modules.automation.KekNuker`
  - `musheor.modules.automation.ElytraTweakz`
  - `musheor.modules.automation.KekBounce`
  - `musheor.modules.features.KekFly`
  - `musheor.modules.features.KekMine`
- В текущей папке `elytra` исходников пока нет.

JAR Musheor содержит `All-Rights-Reserved`, поэтому на первом этапе не следует копировать его код. Лучше сделать мягкую интеграцию через публичный Meteor API и проверку наличия/активности модуля по реестру Meteor.

### Почему это лучше, чем один большой модуль

- `NukerElytraAssist` отвечает только за настройки и включение.
- `MusheorBridge` не дает проекту жестко падать, если Musheor выключен или отсутствует.

- `FlightController` можно тестировать на искусственных событиях без запуска клиента.
- `FlightTrace` позволяет понять, где возник рассинхрон, не меняя сетевое поведение.

## 4. Интеграция с KekNuker

### Базовый вариант

Через `Modules.get()` найти модуль Musheor по его зарегистрированному имени и проверять:

```text
KekNuker существует
KekNuker.isActive()
наш модуль включен
игрок существует и находится в мире
```

Строковое имя нужно подтвердить в первом прототипе, потому что имя класса `KekNuker` и отображаемое имя Meteor могут отличаться. Для этого добавим диагностическую команду/лог, который один раз перечислит модули с `kek`/`nuker` в имени.

### Не делать в первой версии

- Не обращаться к приватным полям `KekNuker` через reflection.
- Не копировать алгоритм выбора блоков из Musheor.
- Не делать обязательную compile-time зависимость от Musheor, если задача решается через Meteor API.
- Не включать или выключать чужой модуль автоматически без отдельной настройки.

## 5. Как фиксировать разрушение блока под игроком

Нужен не один сигнал, а корреляция нескольких наблюдений. Это важно из-за клиентского предсказания и задержки.

### Предлагаемый конвейер

1. На каждом клиентском тике запоминать:
   - позицию игрока;
   - блок под ногами;
   - блоки в небольшом радиусе под игроком;
   - `onGround`, `fallDistance`, состояние элитр.
2. Наблюдать события Meteor/Fabric, связанные с:
   - попыткой начать ломание;
   - отправкой/получением пакетных изменений блока;
   - обновлением блока в клиентском мире.
3. Создавать `BreakObservation` только если:
   - изменился блок под игроком или в зоне его опоры;
   - новый блок действительно не является коллизией;
   - изменение произошло в коротком временном окне после действия `KekNuker`;
   - нет признаков обычного движения с края, телепорта или смены мира.
4. Передавать подтвержденное наблюдение в `FlightController`.

### Приоритет источников

1. Серверное/пакетное обновление блока, сопоставленное с клиентским миром.
2. `BlockUpdateEvent` или эквивалент Meteor.
3. `BreakBlockEvent` только как намерение игрока, но не как окончательное подтверждение.

Если в API Meteor 1.21.11-75 не хватает нужного события, сначала добавить минимальный client-side Mixin только для чтения факта обновления блока. Mixin не должен изменять пакет или физику.

## 6. Двухвекторная траектория и конечный автомат полета

```text
IDLE
  └─ подтвержден слом блока под игроком
       ↓
ARMED
  └─ проверка элитр, активного KekNuker и настроек
       ↓
TARGET
  └─ выбрать ближайший блок сверху и точку на 3-4 блока выше него
       ↓
VECTOR_1
  └─ один быстрый вектор: текущая позиция → точка над блоком
       ↓
VECTOR_2
  └─ один вертикальный вектор вниз: точка над блоком → блок, pitch 90°
       ↓
RECOVER
  └─ немедленно вернуть обычное управление
       ↓
IDLE
```

Важное правило: состояния `ALIGN`, `ASCEND` и отдельного «зависания над блоком»
нет. Первый вектор сразу содержит и вертикальную, и горизонтальную составляющую,
если целевой блок находится не точно над текущей колонной. После достижения
расчетной точки выполняется второй вектор строго вниз.

### Формула траектории

Пусть:

- `P0` — текущая позиция игрока в момент подтверждения разрушения;
- `B` — позиция целевого блока;
- `C(B)` — центр верхней поверхности целевого блока;
- `offset` — 3 или 4 блока;
- `P1 = C(B) + (0, offset, 0)` — точка над блоком.

Тогда план состоит ровно из двух направлений:

```text
V1 = normalize(P1 - P0)
V2 = (0, -1, 0)
```

`V1` выполняется ограниченное число тиков с заданной скоростью, затем управление
переключается на `V2` и выполняется быстрый вертикальный заход. Между `V1` и
`V2` допускается только проверка достижения точки/таймаута, но не коррекция курса
или стабилизация по X/Z.

Для Grim математический вектор не должен превращаться в телепортацию позиции.
`V1` и `V2` являются планом направления для обычного client tick, а фактическая
позиция получается из ванильной физики элитр. Если физика не успевает достичь
`P1` за короткое окно, цикл прекращается, а не компенсируется прямой записью
позиции или серией искусственных movement-пакетов.

Аварийные переходы из любого состояния:

- `ABORT_NO_ELYTRA`
- `ABORT_NO_TARGET`
- `ABORT_COLLISION`
- `ABORT_WORLD_CHANGED`
- `ABORT_TIMEOUT`
- `ABORT_MANUAL_INPUT`
- `ABORT_MODULE_DISABLED`

### Начальные настройки

- `trigger-only-when-kek-nuker-active`: `true`
- `target-height-offset`: 3 блока по умолчанию, допустимый диапазон 3-4
- `scan-up-distance`: например 8-32 блока
- `scan-radius`: 0 по умолчанию; увеличить только если «прямо сверху» не найдено
- `target-standable-only`: `true`
- `vector-1-ticks`: минимальное число тиков для первого вектора, начать с 2-4
- `vector-2-ticks`: минимальное число тиков для второго вектора, начать с 1-2
- `vector-speed-limit`: ограничение скорости первого вектора
- `max-cycle-ticks`: общий таймаут короткого цикла, начать с 6-8
- `abort-on-manual-input`: `true`
- `debug-trace`: `false`

Для первой версии закрепить следующую семантику цели:

1. искать ближайший пригодный блок по направлению вверх;
2. сначала проверять вертикальную колонну текущих X/Z;
3. если `scan-radius` больше нуля, затем проверять соседние колонки по расстоянию;
4. точкой `P1` считать позицию на 3-4 блока выше верхней поверхности найденного блока;
5. не выполнять промежуточное выравнивание после выбора `P1`.

## 7. Elytra и управление движением

Контроллер не должен каждый тик безусловно перезаписывать позицию. Он должен:

1. работать только пока игрок действительно летит на элитрах;
2. сохранять исходные значения до начала автомата;
3. выполнить только два коротких векторных этапа без промежуточного выравнивания;
4. немедленно отдавать управление обратно при ручном вводе или ошибке;
5. не конфликтовать с Meteor `ElytraFly`, `KekFly`, `KekBounce` и другими модулями движения.

Для режима «быстро» длительность фаз должна быть минимальной, но измеряемой:
начать с 2-4 тиков для `V1` и 1-2 тиков для `V2`, а затем подобрать значения
на тестовом мире по фактической скорости элитр. Слишком короткий этап нельзя
компенсировать скрытой отправкой или разделением пакетов.

Перед стартом нужно выбрать политику конфликта:

- рекомендованный вариант: при активном `ElytraFly`/`KekFly` показывать предупреждение и не запускать автомат;
- альтернативный вариант: использовать отдельный адаптер приоритета, но это потребует больше тестов и может давать борьбу модулей.

## 8. Совместимость с Grim v2

### Что следует учитывать

По документации Grim v2:

- движок предсказывает возможное движение игрока 1:1;
- учитываются версия клиента, порядок коллизий и ванильные hitbox;
- Grim ведет персональную копию мира, включая chunk data, block places и block changes;
- изменения мира и задержка компенсируются;
- проверки движения, Timer и Elytra работают независимо от того, насколько быстро
  клиент переключает режимы.

Отсюда следует: нельзя гарантировать, что автомат пройдет любой Grim-сервер.
Надежная стратегия для разрешенного тестового сервера — выполнять только такие
действия, которые может воспроизвести обычная физика Minecraft 1.21.11, и
останавливать автомат, если сервер начал корректировать положение.

### Правила реализации Grim-safe

1. Не использовать `setPosition`, телепортацию игрока, подмену bounding box или
   ручное добавление невозможной скорости.
2. Не создавать, не задерживать, не разделять и не переупорядочивать movement-пакеты
   для сокрытия траектории.
3. Передавать управление через обычный игровой тик и штатную обработку движения;
   один расчет направления на тик, без пачки задним числом.
4. `V1` и `V2` считать желаемыми направлениями, но ограничивать их фактической
   скоростью, ускорением, гравитацией, коллизиями и состоянием glide.
5. Перед началом проверить фактическое состояние элитр, наличие предмета в chest slot,
   отсутствие экрана/телепорта/смены измерения и отсутствие другого модуля,
   меняющего движение.
6. После любого server position correction немедленно сбрасывать `VectorPlan`,
   принимать серверную позицию и ждать нового подтвержденного события.
7. Не запускать второй цикл, пока первый не завершен или явно отменен.
8. Не использовать лаг, fake block, ghost block или высокую задержку как часть
   алгоритма.

### Обработка серверной коррекции

Добавить отдельное состояние `WAIT_SERVER_SYNC`:

```text
VECTOR_1 -> VECTOR_2 -> RECOVER -> WAIT_SERVER_SYNC -> IDLE
                                      └─ correction -> ABORT_SERVER_CORRECTION
```

Если приходит server position/look correction, нужно:

- остановить автомат;
- очистить сохраненный `P1`, текущую фазу и счетчик тиков;
- не отправлять ответную «компенсирующую» серию пакетов;
- дать vanilla-клиенту принять позицию сервера;
- после стабилизации ждать следующий независимый trigger.

Это делает поведение диагностируемым и не превращает рассинхрон в бесконечный
цикл коррекций.

### Параметры тестового стенда

В отчете теста сохранять:

- версию Grim и конкретный commit/build;
- серверную платформу: Fabric или Paper;
- версию серверного Minecraft;
- ping и packet loss;
- включенные проверки Elytra, Timer, NoFall, Phase и BadPackets;
- пороги setback и настройки компенсации задержки.

Результат на одном Grim build нельзя автоматически переносить на другой.

## 9. Пакеты и «silence mode»

В этот план не включается функция, цель которой скрывать движение, разделять или задерживать пакеты для обхода Grim либо другого античита.

Разрешенный технический эквивалент для отладки:

- `PacketTrace`: журнал типа пакета, номера тика и направления;
- `PacketOrderProbe`: проверка порядка уже отправленных клиентом событий;
- `MovementSnapshot`: снимок позиции, yaw/pitch, onGround и состояния элитр;
- тестовый `PacketScheduler` только для лабораторного сервера, если он нужен для воспроизводимости, без подмены движения и без подавления проверок.

Причина: Grim описывает предиктивную 1:1 симуляцию движения, репликацию состояния мира и компенсацию задержки. Поэтому корректная совместимость должна проверяться по физически допустимой последовательности событий, а не по попыткам «размазать» их по пакетам.

## 10. Этапы реализации

### Этап A. Bootstrap

- взять официальный `meteor-addon-template`;
- зафиксировать Minecraft `1.21.11`, Meteor `1.21.11-75`, Java `21`;
- создать `fabric.mod.json`;
- зарегистрировать addon и пустой тестовый модуль;
- убедиться, что `gradlew build` создает JAR.

### Этап B. Диагностический модуль

- добавить `NukerElytraAssist`;
- вывести в чат/лог найденный модуль `KekNuker`;
- добавить переключатель `debug-trace`;
- проверить включение, выключение и сохранение настроек.

### Этап C. Детектор

- реализовать снимки состояния блока под игроком;
- добавить корреляцию с обновлением блока;
- логировать причину принятия или отклонения наблюдения;
- покрыть чистую логику детектора unit-тестами без Minecraft-клиента, где это возможно.

### Этап D. Автомат состояний

- реализовать `FlightState`;
- реализовать `VectorPlan` с `P0`, `P1`, `V1`, `V2` и лимитами по тикам;
- добавить таймауты и аварийные переходы;
- сначала использовать визуальную симуляцию/лог без изменения движения;
- затем включить первый вектор без коррекции курса;
- затем добавить второй вертикальный вектор под 90 градусов;
- проверить, что весь цикл завершается за короткое фиксированное окно.

### Этап E. Grim-safe слой

- добавить обработчик server position/look correction;
- добавить `WAIT_SERVER_SYNC` и `ABORT_SERVER_CORRECTION`;
- запретить прямую запись позиции и искусственное разделение movement-пакетов;
- записывать в trace фактическую позицию, скорость, yaw/pitch, onGround, glide и
  причину остановки;
- прогнать сначала мир без античита, затем собственный сервер с Grim v2.

### Этап F. Конфликты и совместимость

- проверить поведение при включенных `ElytraFly`, `KekFly`, `KekBounce`;
- проверить выход из мира, смерть, телепорт, смену измерения и ручное отключение;
- проверить отсутствие compile-time падения без Musheor;
- проверить логи при разных версиях/сборках Meteor.

### Этап G. Тестовая сборка

- собрать JAR;
- установить только в отдельный Prism-профиль;
- использовать локальный сервер с Grim и отдельный мир без античита для сравнения;
- сохранить логи и таблицу результатов.

| T12 | сервер без Grim | сравнить только физическое поведение и стабильность |
| T13 | цель смещена по X/Z | `V1` сразу содержит горизонтальную и вертикальную составляющие, отдельного выравнивания нет |
| T14 | точка `P1` достигнута | сразу начинается `V2` строго вниз под 90 градусов |
| T15 | короткий цикл | `V1` и `V2` завершаются в пределах `max-cycle-ticks` |
| T16 | vanilla-физика не успела достичь `P1` | цикл прекращается без записи позиции и без искусственных movement-пакетов |
| T17 | Grim отправил server position/look correction | `ABORT_SERVER_CORRECTION`, принятие позиции сервера, новый trigger не создается |
| T18 | проверка порядка пакетов | addon не задерживает, не разделяет и не переупорядочивает movement-пакеты |
| T19 | разные ping/packet loss | нет двойного запуска и бесконечного цикла коррекций |
| T20 | другой Grim build или серверная платформа | результат записан отдельно, настройки и версия стенда указаны |

## 12. Критерии готовности первой рабочей версии

- проект собирается без ручного редактирования JAR;
- addon загружается рядом с Meteor и Musheor;
- модуль не активируется при выключенном `KekNuker`;
- один сломанный блок вызывает максимум один цикл автомата;
- все аварийные состояния возвращают управление игроку;
- в логах можно восстановить последовательность: событие блока -> цель -> состояние -> остановка;
- нет скрытого изменения пакетов и нет функции обхода античита;
- тесты T01-T20 проходят на локальном профиле.
